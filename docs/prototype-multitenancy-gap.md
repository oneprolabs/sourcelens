# 新全站原型与多租户设计对照

- 日期：2026-11-11
- 原型：`https://hyperbdr.github.io/product-prototypes/products/sourcelens/prototypes/fullsite-prototype/#/lenset`
- 评审方式：ego-browser 遍历页面路由（用户端 / 租户管理 / 平台控制台）、三个角色视角、各页“设计说明”
- 关联文档：`docs/multitenancy-review.md`（架构与数据库评审）
- 结论：**原型把产品形态讲清楚了，但没有把安全边界讲清楚。** 它确认了“平台 / 租户 / 用户”三层和“代管”模式，同时把角色模型收缩为 2 个固定租户角色；最大的未决问题是“节点是否允许租户私有”以及共享节点上如何真正隔离 Run。

> 本文是产品原型对照，不是实施计划。原型中的数字为示例数据；原型自己标注的“待后端”“需后端支持”应作为需求输入，而不是已完成能力。

### 0. 已确认决策（2026-11-11）

1. **一个用户只能属于一个租户**：不实现应用内租户切换；租户从 `TenantMembership` 唯一关系推导。
2. **角色权限内置，只保留三个角色**：普通用户、租户管理员、超级管理员；不建可配置 RBAC 表。
3. 因此 §3.3 与 §3.4 从“缺口”改为“已决策”；后续 MVP 范围据此收缩。

---

## 1. 原型在讲什么

原型有三个壳：

| 壳 | 入口 | 主要页面 |
|---|---|---|
| 用户端 | 登录后进入助手 | 聊天、会话历史、我的分享、公开问答列表/详情、设置 |
| 租户管理 | `管理 · <租户>` | 概览、配置向导、助手、问答历史、QA 榜单审核、评估、环境变量、知识库、能力市场、连接、租户信息、成员、组、API Key、LLM 用量、通知 |
| 平台控制台 | `平台控制台` | 全局概览、租户与代管、租户统计、成员总览、API Key 总览、节点、节点设置、官方目录、平台模型、任务、通知、审计日志、全局配置 |

三个角色视角：

- **普通用户**：只使用助手、管理自己的分享。
- **租户管理员**：管理本租户资源、成员、组、API Key、通知。
- **超级管理员**：管理平台、租户生命周期、共享节点、官方目录、全局配置；**不能直接进入租户内容，必须“进入租户（代管）”**。

平台控制台明确写着：

> “超级管理员默认不直接管理租户内容。要帮某个租户配置，请到「租户与代管」点‘进入租户’（代管，操作会被审计）。”

这与此前 GPT 的建议一致：平台管理员不是每个租户的隐式管理员。

## 3. 原型暴露的新问题与矛盾

### 3.1 最高优先级：节点到底允不允许“租户私有”？

原型内部存在直接矛盾：

**A. 节点页设计说明：**

> “所有节点都由平台管理、默认共享……**没有‘租户私有节点’这个概念**，所以不再有单独的‘全部节点’页。”

**B. 创建租户向导第 2 步：**

> “选择这个租户可以使用哪些共享节点……**也可以不选，让租户自己注册私有节点。**”

**C. 配置向导页：**

> `acme-node-01 · 在线（私有）`
> `shared-node-01 · 在线（共享）`

**D. 节点页数据：**

> 可见范围：全部租户 / 仅指定租户 / 全部，排除 1 个租户；每租户并发 ≤6。

这四种说法不能同时成立。它直接决定：

- `LensNode` 是否需要 `tenant_id` / `owner_type`；
- 租户管理员是否需要节点注册、token、生命周期管理；
- 执行隔离是“每租户独立节点/容器”还是“共享节点 + 每 Run 沙箱”；
- 节点可见性是“安全边界”还是仅“调度/配额”。

**结论：这是原型最需要先拍板的一件事。** 在拍板前，不能据此设计 `LensNode` 表，也不能对外宣称“租户隔离已完成”。

### 3.2 “同节点租户隔离”只有声明，没有机制

节点页设计说明写：

> “多租户隔离：同一节点上各租户的 Run 与工作区互相隔离，租户之间看不到彼此。”

但原型没有展示任何机制：

- 没有“每 Run 独立容器 / sandbox”的配置；
- 没有“租户工作区根目录”或“节点数据域”的设置；
- 没有“节点凭据/租户凭据”的隔离；
- “每租户并发”只是限流，不是隔离。

对照当前代码：`trusted_container` 直接把 shell 委托给 LensNode 进程，`/workspace` 共享，datasource 以 symlink 挂入 session。**仅靠节点可见性和并发限制，无法实现原型声称的隔离。**

结论：原型可以作为 UI 目标，但不能作为安全验收依据；执行面必须单独设计（ExecutionBroker + 每 Run gVisor，或至少独立 workspace + 禁止跨租户共享可写目录）。

### 3.3 多租户成员与“租户切换”没有 UX / 协议（已决策：一用户一租户）

原型中：

- 用户菜单只有“返回对话 / 我的分享 / 设置 / 外观 / 退出登录”，**没有切换租户**；
- 登录页没有租户选择、没有子域名/租户标识输入；
- 聊天页只显示助手名与“公开 · slug”，没有当前租户标识；
- 租户管理页顶部固定显示“租户管理员 · Acme 科技”。

**已确认：一个用户只能属于一个租户。** 因此：

- 不需要租户切换器；
- 登录后从 `TenantMembership` 直接推导租户；
- JWT 不需要 tenant claim，每次请求校验 membership 状态即可；
- 成员被移除后，后续请求立即失效（`auth_version` 可放在 membership）；
- 邀请已属于其他租户的邮箱必须拒绝，或走人工“迁移租户”流程（产品需补明确文案）。

结论：这一项从“缺口”变成“简化”。代价是放弃跨租户成员能力；如果未来产品需要，必须改 `UNIQUE(user_id)` 约束并补切换协议。

### 3.4 角色模型被收缩为 2 个固定租户角色（已决策：三角色内置）

原型只有：

- 租户管理员
- 普通用户

外加“用户组”用于助手访问授权；平台侧还有“超级管理员”。

**已确认：角色权限内置，只保留三个角色**：

| 角色 | 层级 | 能力 |
|---|---|---|
| 普通用户 `member` | 租户 | 使用可见助手、管理自己的会话/分享 |
| 租户管理员 `tenant_admin` | 租户 | 管理本租户助手、知识库、连接、环境变量、成员、组、API Key、通知、评估 |
| 超级管理员 `super_admin` | 平台 | 平台控制台、租户生命周期、共享节点、官方目录、全局配置、平台审计；进入租户内容必须代管 |

因此不建 `roles / permissions / role_permissions / membership_roles` 表；权限矩阵写在代码里。`AssistantAccess` 继续承担用户/组对助手的可见性授权。

结论：原型给出了一个**更小的 MVP 范围**，数据库计划应据此收缩，而不是继续按 20 张表推进。

### 3.5 代管缺少治理字段与流程

原型中“进入租户（代管）”：

- 一键进入，顶部红色提示条，可配置模型/节点/知识库/助手；
- 成员、用户组、角色、权限不可见；
- 审计里记为“进入代管 / 代管配置变更”；
- 详情只有：类型、操作、对象、租户、操作人、来源 IP、结果。

缺少：

- 代管原因；
- 代管期限 / 到期时间；
- 代管范围（允许哪些动作）；
- 代管会话 ID（无法把同一会话的多个操作串起来）；
- 审批人 / 被代管租户确认；
- 只读模式 vs 可操作模式；
- 退出/撤销的即时性；
- 代管期间创建的助手/知识库归属谁（`created_by` 是平台用户还是租户？）。

这与 GPT 的建议差距很大。若代管是核心动作，至少需要“原因 + 期限 + 范围 + 审计会话 ID”，否则无法满足企业审计。

### 3.6 租户侧没有审计

平台审计页设计说明写：

> “租户内部的操作审计由租户侧另行提供。”

但租户管理导航里没有“审计日志”。租户管理员会做：

- 邀请/停用成员；
- 改角色、改组；
- 创建/删除助手；
- 创建/吊销 API Key；
- 修改知识库凭证；
- 配置通知渠道。

这些都需要租户级审计。原型目前把它们留给“以后”，但企业客户通常在上线时就会问。

结论：租户审计应作为 S1/S2 的 P1，至少记录成员/角色/API Key/助手/凭证的变更，字段级脱敏。

### 3.7 API Key 只有“可访问助手”，没有动作/配额/IP

原型创建 API Key 只有：

- 名称、用途说明；
- 可访问助手（全部 / 指定）；
- 有效期（30 天 / 90 天 / 1 年 / 永不过期）。

没有：

- 动作范围（只读 / 可执行 / 可管理）；
- 速率限制；
- 日/月配额；
- IP allowlist；
- 轮换过渡窗口（只有“轮换”动作）；
- 调用明细（设计说明说“需后端 issue #38”）。

这与之前设计里的 `api_key_scopes` / `api_key_permissions` / `api_key_ip_allowlists` / 配额表有差距。

对 MVP 可以接受“只限助手 + 过期 + 吊销”，但必须补：

- 每 Key 速率限制（防泄露后被刷）；
- 最近使用时间；
- 调用审计（至少记录 key/tenant/assistant/run/result）；
- 轮换时旧 Key 的宽限窗口。

### 3.8 “公开可见 = 匿名直接使用”，当前后端不支持

助手创建第 4 步写：

> “公开可见：**任何人免登录就能直接使用这个助手的能力**；适合对外的客服、文档问答。”

但当前代码的 `PublicAssistantView` 只返回 `name/description/slug`，匿名不能创建 Session/Run。原型又出现“公开问答列表 → 登录 / 提问”，两者语义不完全一致。

需要明确：

1. **公开 = 只读元数据 + 公开问答**（当前代码，较安全）；
2. **公开 = 匿名可发起 Run**（原型文案，需要匿名 principal、配额、限流、执行隔离、成本控制）。

如果选 2，必须补：

- 匿名租户上下文（从公开助手反查 tenant）；
- `public_run.execute` 能力，而不是给匿名用户普通 `assistant.use`；
- 每 IP / 每助手 / 每租户 / 每分享 token 四层限流；
- 匿名 Run 的并发/时长/token/工具/数据源限制；
- 公开面不得暴露私有 datasource/credentials/内部 Prompt。

结论：这是产品与安全的交叉决策，不能只按 UI 文案实现。

### 3.9 租户设置、配额、存储、导出/删除缺失

原型有：

- 租户信息（名称/简介/语言/时区/联系邮箱/Logo）；
- 知识库页显示“31.2 / 50 GB · 待后端”；
- 节点“每租户并发”；
- 全局配置（平台统一）。

缺少：

- 租户级设置覆盖（`TenantSetting`）；
- 租户配额（并发 Run、每日 Run、Token、费用、存储、API 调用）；
- 存储用量的真实采集；
- 租户导出、删除、legal hold；
- 单租户恢复；
- 计费/套餐（原型明确“额度功能尚未上线”）。

这些可以延后，但**存储用量**和**每租户并发**是原型已经展示的指标，必须明确“是示意还是承诺”。如果是承诺，需要 S2/S3 补采集与配额。

### 3.10 已做对的部分：平台聚合与租户内容分离

平台概览、租户统计、成员总览、API Key 总览都强调：

- 只看汇总，不看对话/成员明细；
- 需要处理具体问题 → 进入租户（代管）；
- 平台只能停用/吊销 Key，不能创建或查看。

这比很多 SaaS 的“平台超管万能”更安全，应保留。

### 3.11 原型自报的后端缺口（应作为需求输入）

原型页脚明确列出：

| 指标 | 现状 |
|---|---|
| 按租户拆分的统计 | 后端没有 tenant 字段，当前只能全平台合计 |
| 每租户/每知识库存储占用 | 未见采集，`LensNode.last_metrics` 待确认 |
| API Key 最近使用/调用次数 | issue #38 未实现，没有 AccessKey 与调用记录 |
| 公开分享访问量 | 分享模型没有访问计数字段 |
| 答案证据覆盖率 | `Run.citations` 有数据，但覆盖率口径未定义 |
| 服务可用性 SLA | 只有最近心跳，没有历史可用性 |

这六项正好对应我们之前风险登记表中的 OPS/EVAL/DSC 类问题。原型把它们显式化，**建议直接转成 acceptance criteria**。

| 通知 | `NotificationChannel/Rule/Recipient` + tenant | 全局 |

## 5. 修订后的 MVP 范围

结合原型，建议把之前的 S1 范围进一步收缩：

### 必须做（S0–S2）

1. **租户内核**：`tenants`、`tenant_memberships`（`UNIQUE(user_id)`、status、role enum、auth_version）；登录后直接从 membership 解析租户，不做切换。
2. **三角色内置**：`member` / `tenant_admin` / `super_admin`；租户 membership 只存前两个，`super_admin` 用 `Profile.platform_role`（或独立字段）标识。
3. **助手可见性**：`public / tenant / restricted`；restricted 支持组 + 用户；分享可见性不得超过助手。
4. **核心资源 tenant_id**：Assistant / DataSource / DataSourceCredential / Connection / EnvironmentVariableSet / Session / Run / RunOutputFile / RunTraceEvent / CredentialLease。
5. **平台代管**：至少“原因 + 期限 + 范围 + 审计会话 ID + 只读/可操作”；成员/组/角色在代管中不可见（原型已定）。
6. **API Key MVP**：tenant + assistant allowlist + expiry + revoke + last_used + rate limit；调用记录可后补。
7. **平台审计 + 租户审计**：至少成员/角色/API Key/助手/凭证变更；字段级脱敏。
8. **执行面隔离**：在开放多租户 Run 之前完成；共享节点必须每 Run 沙箱/独立 workspace；或改为每租户私有节点（需先拍板）。
9. **匿名公开面决策**：若 public 允许匿名 Run，必须补匿名 principal + 配额/限流；否则 public 只做元数据 + 公开问答。

### 可以延后

- 自定义角色 / 权限矩阵 UI（已决定不做，权限矩阵内置）；
- `tenant_roles / permissions / role_permissions / resource_grants` 表（已决定不做）；
- BYOK / 每租户 KMS；

## 6. 需要确认的决策

1. ~~**一个用户能否属于多个租户？**~~ **已确认：只能属于一个租户**，不做切换。
2. **节点是否允许租户私有？**
   - 允许：`LensNode` 加租户归属/注册 token/租户管理；
   - 不允许：所有节点共享，必须做每 Run 沙箱。
3. **public 是否允许匿名 Run？**
   - 允许：匿名 principal + 四层限流 + 执行隔离；
   - 不允许：public 只做元数据 + 公开问答（与当前代码一致）。
4. ~~**MVP 是否只用固定角色？**~~ **已确认：三角色内置**（普通用户 / 租户管理员 / 超级管理员），不建 RBAC 表。
5. **租户审计是否上线即需要？**
   - 是：S1/S2 必做；
   - 否：明确风险并给出补做时间。
6. **代管是否需要审批与期限？**
   - 建议至少“原因 + 期限 + 范围 + 审计会话 ID”；审批可后置。
7. **API Key 是否只做助手范围？**
   - 建议 MVP 加 rate limit + last_used；动作范围/IP/配额后置。
8. **邀请已属于其他租户的邮箱怎么处理？**
   - 拒绝并提示“该账号已加入其他租户” / 平台人工迁移租户 / 要求使用另一个邮箱；需要产品文案与后端错误码。

## 7. 验收清单（原型驱动）

### 7.1 跨租户攻击矩阵（沿用主评审文档 12 项）

1. A 使用 B 的 Assistant/DataSource/Run ID；
2. A 调用 B 的 credential reveal；
3. 匿名访问 B 的 private/tenant Assistant；
4. A 下载 B 的附件/RunOutputFile；
5. A 命中 B 的实时状态缓存；
6. A 订阅 B 的 Run group；
7. A 的 Celery Job 执行 B 的任务；
8. 非 owner DB 账号跨租户 SELECT/UPDATE/DELETE；
9. A 的 Run 使用 B 的 CredentialLease；
10. MCP endpoint 访问内网/云 metadata；
11. Membership/API Key/Delegation 撤销立即生效；
12. Django admin 不能跨租户读取/批量修改。

### 7.2 原型状态验收

- 空 / 少量 / 正常 / 海量数据量；
- 正常 / 加载中 / 加载失败 / 无权限 / 离线；
- 有未保存修改 / 保存失败；
- 移动端卡片；
- 浅色/深色/跟随系统；
- 无权限页不泄露资源是否存在（统一 404/403 策略）。

### 7.3 平台 / 租户边界验收

- 平台管理员不进入代管时看不到租户成员、对话、助手详情；
- 代管时看不到成员/组/角色/权限；
- 代管操作有原因、期限、范围、会话 ID、来源 IP；
- 租户管理员不能修改平台角色、其他租户、平台节点/全局配置；
- 平台只能停用/吊销 API Key，不能创建或查看 Key；
- 平台统计不含原始内容；
- 租户审计可查成员/角色/API Key/助手/凭证变更。

---

## 8. 与主评审文档的关系

- 架构与数据库风险：见 `docs/multitenancy-review.md`。
- 本文补充的是**产品原型对架构的反向约束**：
  - 原型把角色模型收缩为 2 个固定角色 → 主文档的完整 RBAC 可延后；
  - 原型把代管做成核心动作 → 主文档的代管 ADR 需要补“原因/期限/范围/会话 ID”；
  - 原型把 public 定义为匿名可用 → 主文档的 public 语义需要重新决策；
  - 原型的节点页与创建向导矛盾 → 主文档的 `LensNode` 归属与执行隔离 ADR 需要先拍板；
  - 原型明确列出六项后端缺口 → 主文档的 OPS/EVAL/DSC 风险应转成验收项。

---

## 9. 一句话结论

**原型的产品分层是对的，但它不是安全设计。** 一用户一租户和三角色内置已经消除了“租户切换 / 自定义 RBAC”两类复杂度；剩下的三个问题必须在 S1/S4 前回答：**共享节点上 Run 怎么隔离、代管受什么约束、公开是否匿名可执行**。在这三个问题拍板前，按原型直接建表会做出一个“看起来多租户、实际上仍共享执行面”的系统。

## 53. 助手列表、会话和管理接口的权限边界（2026-11-19）

- 匿名预览只返回启用中的公开助手的名称、描述和 slug；非公开、停用、已归档、系统助手及已停用租户的助手不提供匿名预览。这取代 `multitenancy-review.md` §2.3 B 记录的旧直链契约。公开助手发起对话仍需登录或使用有效凭证。
- 普通成员只能查看和使用对本人开放的助手。使用接口不返回数据源绑定、运行配置或访问授权等管理数据；本租户管理员可以管理本租户助手，外租户管理员对公开助手仍只有使用权限。明确授权和租户 API Key 的助手范围也不授予管理权限。
- 会话绑定的助手与路由模式由创建流程决定，之后不可改绑；标题和符合权限的智能协作范围仍可编辑。系统协调助手只能在同租户的智能协作会话中执行，不接受普通助手会话入口。

## 54. 多租户 API 隔离复审（2026-11-19）

| API 范围 | 服务端规则 |
| --- | --- |
| 知识库、连接、来源凭据、环境变量 | 活跃租户管理员只管理本租户记录。旧 staff 兼容仅访问无租户记录，不能查询全库，也不能将外租户连接或凭据关联到无租户知识库。知识库批量状态轮询与详情使用相同的归属范围。 |
| 租户资料、目录、凭据明文、节点连接测试 | 有效代管仅覆盖选中的活跃租户；只读模式不能修改资料或目录、查看凭据明文或发起连接测试。无效格式、过期、已退出或不属于当前操作者的代管均不能取得目标租户权限。 |
| 旧成员、组与角色管理 API | 限旧未归属用户、组、角色；已关联租户或平台身份的记录不能通过旧接口管理。混合批量目标在写入前整批拒绝。 |
| 插件调用审计 | 按来源运行或知识库归属过滤；管理权限以租户角色或可用的旧无租户范围为准。 |
| 问答分享审核与待办数 | 同时检查助手和运行所属租户；历史快照已无运行时要求可归属的本租户发布者。公开助手的使用权不把外租户会话纳入审核。 |

公开助手、显式公开分享、已发布平台目录保留各自的公开规则。平台治理仍按平台管理员权限开放。此轮结论限应用 HTTP API；独立的 Django 运维后台、数据库直连和共享 LensNode 容器上的执行隔离不在 API 回归覆盖内。
