# 抓材料——渐进取证，不做自动全量扫描

这是 `engineering-report` 技能第三步引用的文件，抓材料之前必须读完全文。

## 首轮：每个数据源只取一次活动汇总

根据已加载 Plugin 的工具描述，优先选择可在给定时间窗内覆盖本次授权资源的活动汇总工具。每个
数据源只调用一次；并发执行是允许的，但不要为此使用 `task` 子代理。

汇总结果是默认的事实基础。它通常已整合提交、PR/MR、Issue 等活动；不要再调用同一数据源的
`commit-list`、`issue-list`、`pull-request-list`、搜索或分页工具来重复确认相同范围。

## 阅读已保存的证据

汇总回执中的 `record_count` 是该次来源快照的记录数，不是全部来源的总数。
使用通用运行时的 `read_tool_evidence` 阅读已保存的规范化记录；页面的 `total_records` 才是当前
全部已调用来源的累计条数。`sources` 中每个快照分别保留工具、连接、参数与覆盖缺口，不能把某个
来源的失败套到其他来源上。顺序跟随实际返回的 `next_page`，不要自行推算 offset，也不要并发读页。
`read_progress.complete=true` 后立即停止；摘要或修订后优先重读已保存证据，不重新请求相同来源。

这些分页读取本地已保存的账本，不属于来源补查；应读完所需证据，再由模型归纳事项和判断结论。

## 补查：只补足明确的证据缺口

只有出现下列任一情况才补查：

- 汇总工具明确报告覆盖不全、截断或错误；
- 某项已在汇总中出现，但缺少决定“完成 / 进行中 / 风险”归类的必要信息；
- 用户明确要求某个仓库、项目、人员或编号的细节。

每个数据源最多进行两次补查。补查必须使用汇总结果中已出现的具体仓库、项目、人员或编号；不允许
按所有授权仓库、项目或人员重新枚举，不允许自动遍历远端 API 页，也不允许为寻找更多事项扩大时间窗。超过此
范围时，保留已有证据并在报告的风险或覆盖说明中说明限制。

## 整理与透明度

以汇总和补查的精简结果按账号分组后，再依据工作区指引映射成真实姓名。区分实现、验证/收尾和
报告/发现角色；不要把状态变更者误作实现者。若某数据源不可用或覆盖不足，如实说明其影响，不以
猜测补全。
